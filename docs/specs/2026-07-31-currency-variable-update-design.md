# 铜币货币制与双阶段变量更新设计

## 概述

修正暮归旅店的货币尺度，并将 AI 变量更新拆分成职责明确的日常更新与归寝日结两阶段。所有金额以铜币整数存储；普通对话结束自动执行日常更新；点击归寝时先完成本轮日常更新，再由前端执行确定性日结，最后额外执行只负责跨日语义判断的归寝更新。

## 目标

- 统一货币关系：`1 金币 = 100 银币 = 10,000 铜币`，基础单位为铜币。
- 保持现有变量数值不变；`50000` 从此明确表示 `50000 铜币 = 5 金币`。
- 所有金额字段统一存储、运算和更新为整数铜币。
- 清理并合并 `变量更新指导.txt` 中重复、冲突的初稿，保留唯一一套日常规则和唯一一套归寝规则。
- 使用 `变量更新输出格式.txt` 统一 AI 的 MVU JSON Patch 输出协议。
- 保证归寝不会重复执行即时更新或前端已经完成的确定性结算。

## 非目标

- 不把现有资金或价格整体乘以 100。
- 不保留两套互相竞争的变量规则版本。
- 不让归寝规则重新处理本轮消费、奖励、库存、经验或即时关系变化。
- 不让 AI 重算可以由前端从变量快照确定得到的日结事实。

## 货币模型

### 存储与计算

以下字段以及一切具有金额语义的新增字段都使用整数铜币：

- `旅店.资金`
- `当日预报.日初资金`、`当日预报.当前资金`、`当日预报.今日盈亏`（字段存在时）
- `旅店.员工.${员工名}.职业信息.日薪`
- `建筑.已建成.${建筑名}.维护费用`
- 配方售价、商品价格、采购价格、建造费用、任务货币报酬等

AI 遇到自然语言金额时必须先换算。例如 `2金币3银币8铜币 = 20308`。写入金额时只允许整数，不允许把带单位的文本写入数值字段。

### 展示

使用一套共享格式化函数拆分铜币：

- `50123 → 5金1银23铜`
- `10000 → 1金`
- `150 → 1银50铜`
- `23 → 23铜`
- `0 → 0铜`
- `-10123 → −1金1银23铜`

HUD、当日预报、今日变化和每日账簿统一使用该格式。零值高位省略，负数只在整体最前显示一次负号。

## 双阶段更新流程

### 普通对话

```text
主模型生成剧情
  → 自动执行日常更新一次
    → 写回本轮即时变化
```

### 点击归寝

```text
主模型生成归寝剧情
  → 执行日常更新一次，处理本轮即时变化
    → 前端脚本执行确定性日结
      → 额外执行归寝更新一次，只处理跨日语义变化
        → 前端重新锁定确定性事实并写回
```

## 日常更新规则

日常更新每次主模型回复结束后自动触发，只依据当前回复、必要的最近上下文和主生成前变量快照。

负责：

- 行动造成的精力、压力和当天时间变化；
- 消费、采购、销售、奖励等即时资金变化；
- 库存、经验、满意度、声望和员工关系变化；
- 建造、探索、任务、叙事种子的即时变化；
- 播种、浇水、施肥、收获等玩家当下执行的农牧操作；
- 资金变化后同步当前资金与今日盈亏。

禁止：

- 推进天、星期、季节、年份或生成次日天气；
- 执行睡眠恢复；
- 扣除员工日薪、建筑维护费；
- 递减作物剩余天数或重置农田每日标记；
- 递减特殊效果天数、判断任务跨日超时；
- 重算设施引力、总引力或生成次日预报。

## 归寝更新规则

归寝更新只在点击归寝后额外触发，并且位于日常更新和前端确定性日结之后。

负责：

- 大掌柜与员工休息后的精力恢复；
- 压力、士气、忠诚度等跨日语义变化；
- 日期、星期、季节、年份和次日天气；
- 特殊效果期限、任务期限与任务种子激活；
- 作物成熟、过熟、缺水、魔力稳定等需要语境判断的后果；
- 建筑产出状态、访客生态语义项、次日预报和注意事项。

禁止：

- 重做本轮日常更新中的消费、奖励、库存、经验和即时关系变化；
- 重复任何前端已经完成的确定性结算。

## 前端确定性日结契约

实施前以自动化测试逐项确认现有脚本确实完成以下功能；缺失或不完整的项目必须先补齐，再把它声明为 AI 禁止更新项：

1. 汇总并扣除所有员工日薪；
2. 汇总并扣除所有已建成建筑维护费；
3. 对普通与魔法农田中种植中的作物执行 `剩余天数 - 1`，且不低于零；
4. 重置普通农田 `今日已浇水`，以及魔法农田 `今日已浇水`、`今日已魔力灌溉`、`今日已养护`；
5. 按所有已建成建筑的六维影响力逐维求和，写入设施引力，并据此更新总引力；
6. 将日薪和维护费从资金扣除，记录并保留日结后的资金；
7. 使用结算标识防止同一归寝重复扣费或重复推进；
8. AI 归寝更新写回后，再次覆盖并锁定上述确定性资金、农田和引力事实。

已定位的现有实现位于 `js/mvu.js`：`settleDay()` 负责 1–7，`enforceSettlementFacts()` 负责 8。现有 `test/api.js` 已覆盖这些主路径；实施时将补强边界断言并确保货币单位说明与测试命名一致。

## AI 输出协议

`变量更新输出格式.txt` 作为独立的固定格式条目，由日常和归寝规则共同引用。唯一正式协议为：

```xml
<UpdateVariable>
<Analysis>
- time passed: 本轮剧情经过的时间
- dramatic updates allowed: yes 或 no，并说明判定依据
- checked changes: 本阶段有依据的变量变化摘要
</Analysis>
<JSONPatch>
[
  { "op": "delta", "path": "/旅店/资金", "value": -1250 }
]
</JSONPatch>
</UpdateVariable>
```

约束：

- 一个回复只输出一个完整 `UpdateVariable` 标签，不使用 Markdown 代码围栏；
- `JSONPatch` 必须是合法 JSON 数组；无变量变化时使用 `[]`；
- 路径采用 JSON Pointer，并正确转义 `~` 和 `/`；
- 已有值整体替换使用 `replace`，数值增减优先使用 `delta`；
- 新增对象键或数组项使用 `insert`，删除使用 `remove`，确有必要时才使用 `move`；
- 不更新 `_` 开头的只读字段；
- 只更新当前阶段职责内、且有当前回复依据的变量；
- 分析保持简短，不得在分析中虚构变量变化；
- 所有金额 patch 值为整数铜币。

`变量更新输出格式.txt` 不做过度删减。保留并扩充现有的分析步骤、各操作定义、合法 JSON 要求、只读字段限制和完整格式骨架，同时补入以下防误更新护栏：

- 逐条对照对应变量的 `check`，没有当前回复证据就不更新；
- 分析当前阶段（日常或归寝）并排除另一阶段的职责；
- 使用更新前快照计算 `delta`，禁止把目标值误当增量；
- 写 patch 前检查路径和父级是否存在，并据此选择 `replace` 或 `insert`；
- 同一变量在一个数组中只保留一条最终操作，避免先增后改或重复扣除；
- 新增、删除对象或数组项必须有明确剧情依据；
- 不猜测未出现的消费、奖励、时间流逝、角色态度或随机结果；
- 归寝时先读取脚本确定事实清单，禁止输出会覆盖这些事实的 patch；
- 给出金额换算、数值增减、对象新增、数组追加、删除和无变化六类正确示例，并列出把金币文本直接写入数值字段、使用错误路径、输出非 JSON 等反例。

网页第二 API 提示、提取逻辑和测试必须与此 JSON Patch 协议同步，不再把 `_.set / _.add / _.remove` 作为正式输出格式。

## 文件职责

- `变量更新指导.txt`：唯一一套日常规则与唯一一套归寝规则，说明触发时机、变量职责和禁止重复项。
- `变量更新输出格式.txt`：两种更新共同使用的固定 JSON Patch 协议、路径规则和最小示例。
- `js/render.js` / `js/app.js`：统一铜币展示。
- `js/api.js` / `js/extract.js`：向第二 API 提供正确协议并提取完整 JSON Patch 更新标签。
- `js/mvu.js`：确定性归寝结算和 AI 写回后的事实锁定。

## 取舍

采用严格双阶段设计，而不是让归寝替代日常或全量复算。它能保留归寝剧情中的即时变化，同时以清晰边界避免重复扣款、奖励和成长。采用单一 JSON Patch 协议而不是双格式兼容，降低世界书、第二 API、解析器和测试长期漂移的风险。

- 验证所有示例数值按铜币解释，`50000` 显示为 `5金`。
- 逐项测试前端确定性日结契约的八项功能。
- 验证普通对话只触发日常更新。
- 验证归寝严格执行“日常 → 脚本确定性日结 → 归寝 → 事实锁定”。
- 验证同一结算标识不会重复扣薪、维护费或推进作物。
- 验证归寝 JSON Patch 试图改写确定性资金、农田或引力时会被前端纠正。
- 验证两份指导文件不存在重复整章、空内容或互相冲突的协议。
- 运行完整 `npm test` 并在实际页面检查 HUD、预报和每日账簿。
